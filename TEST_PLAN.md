## 1. Что проверяем и что нет

Область проверки по заданию: **каталог - корзина - оформление заказа**,
плюс вход и регистрация в той мере, в какой они нужны для этих сценариев.

### В области проверки

| Подобласть | Что конкретно |
|---|---|
| Каталог | список товаров, поиск, фильтр по цене, сортировка по цене, карточка товара |
| Корзина | добавление товара, изменение количества, удаление, пересчёт сумм, бизнес-правило «один Thor Hammer» |
| Оформление заказа | шаги checkout, адрес доставки (в т.ч. автозаполнение по postcode), способ оплаты (cash on delivery), создание заказа, номер счёта |
| Доступ | изоляция заказов между покупателями, обязательность аутентификации для оформления |
| Ограничения | доступность товара (наличие на складе), цена/количество |

### Вне области проверки (сознательно)

- **Админка** (`/admin`): CRUD товаров, пользователей, отчёты, статистика.
- **Аренда** (rentals) - отдельная витрина с иной логикой ценообразования.
- **Контактная форма** и чат-виджет.
- **Социальный вход (Google/GitHub)** - требует внешних провайдеров, не воспроизводится локально без стенда.
- **2FA/TOTP**, смена и восстановление пароля, профиль пользователя.
- **PDF-инвойсы**, email-уведомления (MailCatcher доступен, но не в приоритете).
- **Кросс-браузерность** как отдельная цель: прогон только в Chromium. Проекты Firefox/WebKit не заведены и в бюджет не входили.
- **Производительность и нагрузка**.
- **i18n** (переключение языка).

Причина: 4 часа. Указанные части не влияют на проверяемый критический путь «найти товар - положить в корзину - оформить заказ», а админка и аренда прямо исключены заданием.

## 2. Риски и приоритеты

Ранжировано по «вероятность × цена ошибки». Приоритет сценариев выводится отсюда.

| ID | Риск | Влияние | Приоритет |
|---|---|---|---|
| R1 | Заказ создаётся при отсутствии товара или в количестве больше остатка | Продажа того, чего нет; отмены, возвраты, отрицательный остаток | **Критический** |
| R2 | Заказ можно оформить с пустой корзиной / на нулевую сумму | Мусорные счета, искажение отчётности и рассылок | **Высокий** |
| R3 | Сумма заказа не совпадает с корзиной (цена, количество, скидка) | Финансовые расхождения, претензии | **Высокий** |
| R4 | Пользователь не может завершить оформление (тупик в UI) | Потеря продаж, обращение в поддержку | **Высокий** |
| R5 | Покупатель видит или оплачивает чужую корзину/заказ | Утечка данных, репутация | **Высокий** |
| R6 | Адрес/индекс принимается в противоречивом виде | Недоставка, ручная правка заказов | Средний |
| R7 | Поиск/фильтр/сортировка возвращают не то, что просили | Пользователь не находит товар | Средний |
| R8 | Ошибки API отдаются без понятного текста (5xx вместо 4xx) | Невозможно разобрать инцидент по логам | Средний |
| R9 | Нестабильность самих автотестов | Доверие к прогону падает, дефекты пропускаются | Средний |

Оценка R4 подтвердилась на практике: в этой сборке кнопка **Confirm требует двух нажатий** (BUG-05). Это ровно тот класс риска, который не виден в API-тестах и находится только сквозным UI-сценарием.

## 3. Порядок проверки (что делали в каком порядке)

1. **Развёртывание** и подготовка данных (вне бюджета 4 часов).
2. **Анализ**: контракты API (`/api/documentation`, роуты), UI-шаблоны (`data-test`-атрибуты), бизнес-правила из кода.
3. **Критический путь через API**: заказ - чтение заказа - сверка суммы. Самый ценный результат за минуту выполнения.
4. **Корзина**: количество, удаление, слияние позиций, бизнес-правило Thor Hammer.
5. **Каталог**: инварианты поиска, фильтра и сортировки.
6. **Доступ**: чужой заказ, обязательность токена, валидация.
7. **UI критический путь**: мастер оформления заказа.
8. **Исследовательские пробы** на границах: наличие на складе, пустая корзина, чужая корзина - здесь найдены BUG-01…BUG-04.
9. **Регрессионные тесты на найденные дефекты** с `test.fail()`.
10. **Документы и решение о релизе.**

## 4. Подход к тестовым данным

- **Свой пользователь на каждый тест.** Регистрация через API (`POST /users/register`) с уникальным e-mail. Демо-аккаунты не используются: после `MAX_LOGIN_ATTEMPTS = 3` неудачных попыток аккаунт блокируется, и общий пользователь превращает один негативный тест в каскад падений (риск R9).
- **База не сбрасывается между тестами.** Тесты не делят состояние: каждый создаёт свою корзину и свой заказ. Прогон не зависит от предыдущих запусков и от порядка выполнения (проверено `--shuffle`).
- **Перед прогоном** рекомендуется `migrate:fresh --seed`: заказы уменьшают остаток товара, и после многих прогонов популярные позиции могут закончиться. Тесты подбирают товар, который реально есть в наличии, но чистый seed делает прогон предсказуемым.
- **Адрес для заказа строится из `GET /postcode-lookup`**, а не выдумывается: API валидирует соответствие города/региона и страны (`AddressMatchesCountry`), и придуманный адрес даёт 422, который легко принять за дефект продукта.

## 5. Вопросы и допущения

Требования - user stories в `docs/user-stories/` и матрица `docs/features.md`; отдельного описания поведения остатков на складе в них нет. Ниже зафиксированы допущения, принятые при проверке, и вопросы, которые я бы задал продукту.

### Допущения

| # | Допущение | На чём основано |
|---|---|---|
| A1 | Товар с `in_stock: false` (остаток 0) заказать нельзя | Соответствующий флаг в API и заблокированная кнопка «Add to cart» в UI |
| A2 | Количество в заказе не может превышать остаток | Стандартное поведение магазина; в ТЗ прямо названо «проверять корректность данных» |
| A3 | Заказ с пустой корзиной недопустим | UI не показывает кнопку перехода при пустой корзине |
| A4 | Корзина принадлежит тому, кто её создал | Ожидание пользователя; в API корзина анонимная (см. BUG-04) |
| A5 | Остаток 25 у товаров категории hand tools - значение сидера, а не бизнес-константа | `database/seeders/ProductSeeder.php` |
| A6 | «После нескольких неудачных попыток аккаунт блокируется» - блокировка наступает на 3-й попытке и не действует на администратора | `UserService::MAX_LOGIN_ATTEMPTS = 3` |

### Открытые вопросы к продукту

| # | Вопрос | Почему важно |
|---|---|---|
| Q1 | Задумано ли, что корзина не привязана к пользователю и `cart_id` достаточно для оформления заказа? | Если да - `cart_id` фактически bearer-секрет, и его утечка = чужой заказ (BUG-04) |
| Q2 | Должен ли остаток уменьшаться при создании заказа, и что происходит при отмене? | Без этого нельзя проверить, что отрицательный остаток - дефект, а не особенность |
| Q3 | Допустим ли заказ на нулевую сумму (например, полностью покрытый скидкой)? | От этого зависит ожидаемый результат TC-22/BUG-03 |
| Q4 | Должна ли кнопка «Confirm» на шаге оплаты срабатывать с первого нажатия? | BUG-05 может быть как дефектом, так и недокументированным двухфазным подтверждением |
| Q5 | Нужна ли проверка остатка на этапе добавления в корзину или только на этапе оплаты? | Влияет на то, где должен стоять валидатор |

## 6. Что не проверено (и почему)

- **Конкурентные заказы последнего экземпляра** (гонка при остатке 1). Требует параллельного сценария с точной синхронизацией - вне бюджета; риск R1 покрыт проверкой количества, но не гонкой.
- **Отмена/возврат заказа и влияние на остаток** - функциональности отмены в области проверки не было.
- **Firefox / WebKit** - проекты не заведены, прогон не выполнялся.
- **Восстановление пароля и 2FA** - вне области.
- **Поведение при недоступном postcode-сервисе** - в коде предусмотрен fail-open (`AddressMatchesCountry`), но сценарий отказа бэкенда не воспроизводился.
- **Нагрузка и rate limiting** - вне области.

## 7. Критерии выхода

Релиз проверенной части считается готовым, если:

1. Критический путь «товар - корзина - заказ» проходит и через API, и через UI.
2. Суммы заказа совпадают с корзиной.
3. Нет открытых дефектов уровня Critical/High в области проверки.
4. Известные дефекты Low/Medium задокументированы и приняты продуктом.

Фактический результат - в `RELEASE.md`.
