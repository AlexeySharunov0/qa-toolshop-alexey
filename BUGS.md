## BUG-01 - Товар с нулевым остатком можно положить в корзину и заказать

**Влияние на пользователя.** Магазин продаёт товар, которого нет на складе.
Покупатель получает подтверждение заказа и номер счёта, а товар не приедет.
Для бизнеса это отмены, возвраты и звонки в поддержку.

**Серьёзность: High. Приоритет: P1.**
Высокая серьёзность: заказ реально создаётся и получает номер, обратной связи
пользователю об ошибке нет. Не Critical, потому что остатки ведёт внешний склад
и часть таких заказов гасится вручную.

**Версия / commit.** `SPRINT=sprint5`, тег `2.5`, commit `9e7736c`.

**Предусловия.** Приложение запущено, БД засеяна, есть авторизованный покупатель.
Товар «Long Nose Pliers» имеет остаток 0 и отдаётся API с `in_stock: false`.

**Шаги воспроизведения.**
1. `GET /products?q=Long Nose Pliers` - взять `id`, убедиться, что `in_stock: false`.
2. `POST /carts` - создать корзину.
3. `POST /carts/{cartId}` с `{"product_id": "<id>", "quantity": 1}`.
4. `POST /payment/check` с `payment_method: cash-on-delivery`.
5. `POST /invoices` с адресом и `cart_id`.

**Ожидаемый результат.** Шаг 3 отклоняется с 4xx (товара нет), шаг 5 - тоже.

**Фактический результат.** Шаг 3 - `200 {"result":"item added or updated"}`.
Шаг 5 - `201`, счёт `INV-2026000004`, `total = 14.24`.

**Доказательства.**
- `reports/evidence/BUG-01.json` - ответы шагов 1, 3, 5.
- `reports/traces/BUG-01-out-of-stock-order.zip` - trace автотеста.
- `reports/screenshots/BUG-01-out-of-stock-product-page.png` - карточка товара:
  «Out of stock», количество и кнопка «Add to cart» заблокированы. То есть UI покупку
  запрещает, а API её принимает - расхождение видно на одном экране.

**Связанный тест-кейс.** TC-20. **Автотест.** `tests/api/known-defects.spec.ts` - `BUG-01 a product with zero stock cannot be ordered` (`test.fail`).

**Где смотреть в коде.** `App\Services\CartService::addItemToCart` и
`App\Services\InvoiceService::createInvoice` - проверки остатка нет ни на одном шаге.
UI блокирует кнопку (`[disabled]="!product.in_stock"`), поэтому дефект виден только
через API.

## BUG-02 - Количество в заказе не ограничено остатком, остаток уходит в минус

**Влияние на пользователя.** Покупатель заказывает 26 единиц товара, которого на
складе 25. Заказ принимается, остаток становится отрицательным (`-2` в этом
прогоне: сидер инвойсов уже успевает списать часть, затем qty=26 уводит колонку
ниже нуля). Дальше
каталог и карточка товара начинают противоречить друг другу, а следующие
покупатели видят некорректную доступность.

**Серьёзность: Critical. Приоритет: P1.**
Critical, потому что портится хранимые данные (отрицательный остаток), а не только
пользовательский сценарий: последствия видны и после исправления заказа.

**Версия / commit.** `SPRINT=sprint5`, тег `2.5`, commit `9e7736c`.

**Предусловия.** БД засеяна. Сидер задаёт остаток 25 для товаров категории hand tools
(`database/seeders/ProductSeeder.php`). Ограничение API на количество в корзине - 99.

**Шаги воспроизведения.**
1. `GET /products?q=Washers` - взять `id`.
2. `POST /carts`.
3. `POST /carts/{cartId}` с `{"product_id": "<id>", "quantity": 26}`.
4. Оформить заказ (`POST /invoices`).
5. `docker compose exec laravel-api php artisan tinker --execute="echo DB::table('products')->where('name','Washers')->value('stock');"`.

**Ожидаемый результат.** Шаг 3 или 4 отклоняется: 26 > 25. Остаток не становится
отрицательным.

**Фактический результат.** Шаг 3 - `200`, шаг 4 - `201`, счёт `INV-2026000005`,
`total = 92.30`. Шаг 5 - `-2` (`DB::table('products')->value('stock')`;
в JSON модели поле `stock` скрыто, Eloquent его не отдаёт).

**Доказательства.**
- `reports/evidence/BUG-02.json`.
- `reports/traces/BUG-02-oversell.zip`.
- Побочный эффект виден в `reports/evidence/BUG-06.json`-подобном состоянии: после
  такого заказа `GET /products` (кеш 300 с) отдаёт `in_stock: true`, а
  `GET /products/{id}` - `in_stock: false`. Наблюдение зафиксировано в разделе
  «Наблюдения» ниже.

**Связанный тест-кейс.** TC-21, TC-25. **Автотест.** `tests/api/known-defects.spec.ts` - `BUG-02 cart quantity is limited by available stock` (`test.fail`).

**Где смотреть в коде.** `CartController` валидирует только `quantity: min:1|max:99`,
остаток не участвует. `InvoiceService::createInvoice` не перепроверяет наличие.

## BUG-03 - Пустую корзину можно превратить в заказ на 0.00

**Влияние на пользователя.** Заказ с нулевой суммой и валидным номером счёта.
Мусор в списке заказов покупателя, в отчётности, в рассылке о заказе.
UI такого не позволяет (кнопка перехода не показывается), API - позволяет.

**Серьёзность: High. Приоритет: P1.**
Не Critical: деньги не теряются, но данные и отчёты загрязняются, а поддержке
приходится разбирать «пустые» заказы.

**Версия / commit.** `SPRINT=sprint5`, тег `2.5`, commit `9e7736c`.

**Предусловия.** Авторизованный покупатель, пустая корзина.

**Шаги воспроизведения.**
1. `POST /carts` - создать корзину, товары не добавлять.
2. `GET /carts/{id}` - убедиться, что `cart_items` пуст.
3. `POST /invoices` с адресом, `payment_method: cash-on-delivery`, этим `cart_id`.

**Ожидаемый результат.** 4xx с понятным сообщением («cart is empty»).

**Фактический результат.** `201`, счёт `INV-2026000006`, `total = 0`, заказ виден в
`GET /invoices`.

**Доказательства.** `reports/evidence/BUG-03.json`,
`reports/traces/BUG-03-empty-cart-order.zip`.

**Связанный тест-кейс.** TC-22. **Автотест.** `tests/api/known-defects.spec.ts` - `BUG-03 an empty cart cannot be turned into an order` (`test.fail`).

## BUG-04 - Любой авторизованный пользователь может оформить заказ из чужой корзины

**Влияние на пользователя.** `cart_id` не привязан к покупателю: если идентификатор
попал к другому человеку (общий браузер, referer, лог, пересланная ссылка), тот
может провести оформление из чужой корзины, и заказ появится **в его** аккаунте.
Владелец корзины при этом теряет товары из неё.

**Серьёзность: High. Приоритет: P1.**
ULID не подбирается перебором, поэтому практическая эксплуатируемость ниже, чем у
классического IDOR - отсюда High, а не Critical. Но контроль доступа отсутствует
как таковой, и это вопрос Q1 в `TEST_PLAN.md`: возможно, корзина задумана анонимной,
и тогда `cart_id` - фактически bearer-секрет, который нигде не описан как секрет.

**Версия / commit.** `SPRINT=sprint5`, тег `2.5`, commit `9e7736c`.

**Предусловия.** Два авторизованных покупателя: A и B.

**Шаги воспроизведения.**
1. A: `POST /carts` - `cartId`, добавить товар.
2. B: `POST /invoices` с `cart_id` из шага 1 и адресом B.

**Ожидаемый результат.** 403/404: корзина принадлежит другой сессии.

**Фактический результат.** `201`, счёт `INV-2026000007`, `total = 3.55`, заказ
принадлежит B.

**Доказательства.** `reports/evidence/BUG-04.json`,
`reports/traces/BUG-04-cart-ownership.zip`.

**Связанный тест-кейс.** TC-23. **Автотест.** `tests/api/known-defects.spec.ts` - `BUG-04 another customer's cart cannot be consumed` (`test.fail`).

**Где смотреть в коде.** `Cart` не имеет `user_id`; `InvoiceController::store`
принимает `cart_id` из тела запроса и не сверяет владельца.

## BUG-05 - «Confirm» на шаге оплаты требует второго нажатия

**Влияние на пользователя.** Покупатель проходит весь мастер, нажимает
«Confirm», видит сообщение «Payment was successful» - и **ничего не происходит**:
заказа нет, подтверждения нет. Кнопка остаётся на экране. Заказ создаётся только
вторым нажатием. Часть пользователей уйдёт на этом шаге, считая, что оплата прошла,
а заказ «завис».

**Серьёзность: High. Приоритет: P1.**
Критический путь в UI не завершается с первого действия, при этом интерфейс
подаёт ложный сигнал успеха. Есть обход (нажать ещё раз), поэтому не Critical.

**Версия / commit.** `SPRINT=sprint5`, тег `2.5`, commit `9e7736c`.

**Предусловия.** Авторизованный покупатель, товар в корзине, пройдены шаги
корзины, входа и адреса.

**Шаги воспроизведения.**
1. Открыть `/checkout`, пройти шаги 1-3.
2. На шаге оплаты выбрать `Cash on Delivery`.
3. Нажать **Confirm один раз**.
4. Подождать 10-15 секунд.

**Ожидаемый результат.** Появляется подтверждение с номером счёта, заказ создан.

**Фактический результат.** Появляется только «Payment was successful».
Запрос `POST /invoices` не отправляется. Второе нажатие создаёт заказ (`201`).

**Причина.** `PaymentComponent::checkPayment()` отправляет запрос только когда
`!this.state`, и сразу возвращает `of(this.state)`. При первом вызове `state` ещё
`undefined`, поэтому `finishFunction` получает `false` и блок создания счёта не
выполняется. Второй вызов возвращает `true` - уже без повторной проверки оплаты,
даже если способ оплаты к этому моменту изменён.

**Доказательства.**
- `reports/traces/BUG-05-confirm-two-clicks.zip` - trace: видно, что после первого
  клика нет `POST /invoices`, после второго он есть.
- Скриншот состояния после первого клика: `reports/screenshots/BUG-05-after-first-click.png`.

**Связанный тест-кейс.** TC-24 (и TC-15, где используется обход). **Автотест.**
`tests/ui/known-defects.spec.ts` - `BUG-05 one click on "Confirm" places the order` (`test.fail`).

## BUG-06 - После `migrate:fresh --seed` каталог отдаёт устаревшие id, add-to-cart падает с 422

**Влияние на пользователя / команду.** Документированная процедура сброса данных
(`docs/getting-started.md` проекта: `php artisan migrate:fresh --seed`) не очищает
кеш приложения. Каталог продолжает отдавать id товаров, которых уже нет в БД, и
любая попытка добавить товар в корзину заканчивается
`422 {"message":"The selected product id is invalid."}` в течение 300 секунд
(`ProductService::CACHE_TTL = 300`). Для QA это означает: прогон автотестов сразу
после сброса БД краснеет по непонятной причине, и дефект легко принять за реальный
баг продукта.

**Серьёзность: Medium. Приоритет: P2.**
Продакшн-пользователи не страдают (ресурс сбрасывают только при инсталляции), но
воспроизводимость окружения и онбординг ломаются. Отдельный эндпоинт
`POST /refresh` кеш как раз чистит - то есть обход существует и используется самим
приложением, просто не в документированной команде.

**Версия / commit.** `SPRINT=sprint5`, тег `2.5`, commit `9e7736c`.

**Шаги воспроизведения.**
1. `GET /products` - прогреть кеш каталога (без этого `migrate:fresh` при пустом кеше дефект **не** проявляется).
2. `docker compose exec laravel-api php artisan migrate:fresh --seed` - **без** `cache:clear`.
3. `GET /products?q=Washers` - запомнить `id`.
4. `docker compose exec laravel-api php artisan tinker --execute="echo DB::table('products')->where('name','Washers')->value('id');"`.
5. `POST /carts`, затем `POST /carts/{id}` с `id` из шага 3.

**Ожидаемый результат.** Id из API совпадает с id в БД; товар добавляется.

**Фактический результат.** Шаг 3 - `01M6HKF00485DPWKMYQSRQBVBP`,
шаг 4 - `01M6HKFKWN4J2C933FDEG6M6D1`. Шаг 5 - `422 The selected product id is invalid`.
После `php artisan cache:clear` id совпадают и добавление работает.

**Доказательства.** `reports/evidence/BUG-06.json`.

**Обход (используется в инструкции README):** после сброса БД выполнять
`docker compose exec laravel-api php artisan cache:clear`, либо ждать 5 минут,
либо сбрасывать через `POST /refresh`, который кеш чистит.

## Наблюдения, предложения и неподтверждённые предположения

Здесь то, что **не является** подтверждённым дефектом в области проверки, но что я
бы отдал команде.

### Наблюдения (воспроизведены, но классифицированы как риск/UX)

1. **Кеш каталога 300 с делает `in_stock` устаревшим.** После того как товар
   распродан, `GET /products` ещё до 5 минут отдаёт `in_stock: true`, а
   `GET /products/{id}` - `false`. Пользователь видит товар в листинге, открывает
   карточку и получает заблокированную кнопку «Add to cart» без объяснения.
   Предложение: сделать TTL короче для `in_stock` или инвалидировать кеш при
   изменении остатка.
2. **Незащищённый `POST /refresh`.** Эндпоинт без аутентификации выполняет
   `migrate:fresh --seed` и очищает кеш, то есть уничтожает все данные. Для
   локального демо-стенда это ожидаемый помощник, но в любом окружении с реальными
   данными это критическая уязвимость. Предложение: закрыть ролью администратора
   или вынести за пределы API.
3. **Ошибка создания заказа не показывается пользователю.** В
   `PaymentComponent::finishFunction` обработчик ошибки `createInvoice` пуст
   (`error: () => { }`). Если сервер вернёт 422 (например, адрес перестал
   соответствовать индексу), пользователь не увидит **ничего**. Предложение:
   показывать `paymentError`, как это уже сделано для проверки оплаты.
4. **Счётчик результатов поиска отстаёт от списка.** Блок «N products found for
   'x'» рендерится до замены карточек, поэтому на долю секунды показывает старое
   число. Не дефект, но тест на это ловко поймать «ложный баг» - стоит
   перерисовывать счётчик и список атомарно.

### Предложения по улучшению (не проверялись как дефекты)

1. Валидировать остаток в одном месте (сервис), а не в контроллере, и возвращать
   409 с текущим доступным количеством.
2. Запрещать оформление пустой корзины и корзины с нулевой суммой на уровне
   сервиса, а не только в UI.
3. Привязать корзину к пользователю на этапе оформления или явно сделать
   `cart_id` подписанным токеном и описать это в документации.
4. Сделать `checkPayment` идемпотентным: возвращать результат проверки, а не
   состояние предыдущего вызова.
5. Сброс БД через `POST /refresh` уже чистит кеш - стоит добавить то же самое в
   документированную artisan-команду (или вообще убрать кеш из `getAllProducts`
   для админских сценариев).

### Неподтверждённые предположения

1. Возможна гонка при остатке 1 и одновременных заказах - **не проверялось**,
   сценарий вне бюджета.
2. Возможен рост остатка при отмене заказа - функциональности отмены в области не
   было, проверить не удалось.
3. Регистр `cart_id` (возвращается в нижнем регистре, а `product_id` - в верхнем)
   выглядит несогласованно, но запросы проходят при обоих вариантах написания;
   воспроизводимого дефекта не нашёл.
