# QA Toolshop - тестовое задание Prionex (QA Engineer, AI First)

Проверка готовности к релизу части учебного интернет-магазина
[Practice Software Testing - Toolshop](https://github.com/testsmith-io/practice-software-testing):
каталог - корзина - оформление заказа.

Автотесты: Playwright + TypeScript, UI и API.

(BUG-01, BUG-03, BUG-04). Подробности в [RELEASE.md](RELEASE.md).

| Параметр | Значение |
|---|---|
| Репозиторий | `https://github.com/testsmith-io/practice-software-testing` |

Почему `sprint5`, а не `sprint5-with-bugs`: в `sprint5-with-bugs` нет страницы
корзины и шагов оформления (единственный монолитный `checkout`), поэтому
обязательную для проверки цепочку «корзина - оформление заказа со способом оплаты»
там нельзя пройти до конца. `sprint5` позволяет проверить критический путь целиком.

Commit зафиксирован тегом, чтобы окружение воспроизводилось однозначно.

## 3. Запуск приложения

Клон приложения держится **отдельно** от этого репозитория: код Toolshop
распространять нельзя, в этом репозитории только тесты и документы.

```bash
# 1. Клон приложения и фиксация версии
git clone https://github.com/testsmith-io/practice-software-testing.git ~/pst-app
cd ~/pst-app
git checkout 2.5          # commit 9e7736c3841ec2bbb9a6822c9e6602353b7b9a65

# 2. Версия приложения
echo "SPRINT=sprint5" > .env

# 3. Запуск (первый раз собирает образы, до 10 минут)
docker compose up --pull missing -d

# 4. Ожидание готовности API (первый старт ~30 с после сборки)
until curl -sf http://localhost:8091/status; do sleep 2; done

# 5. Засев базы
docker compose exec laravel-api php artisan migrate:fresh --seed

# 6. ВАЖНО: очистка кеша каталога (см. BUG-06)
docker compose exec laravel-api php artisan cache:clear
```

Шаг 6 обязателен. `migrate:fresh --seed` пересоздаёт товары с новыми id, но кеш
каталога живёт 5 минут (`ProductService::CACHE_TTL = 300`), и без очистки
добавление в корзину падает с `422 The selected product id is invalid`. Это
воспроизводимый дефект, описан в [BUGS.md](BUGS.md#bug-06).

Приложение готово, когда:

- UI: `http://localhost:4200` отвечает 200;
- API: `curl -s http://localhost:8091/status` возвращает JSON с `"version":"5.0"`;
- Swagger: `http://localhost:8091/api/documentation`.

## 4. Запуск автотестов

```bash
# из корня этого репозитория
cp .env.example .env          # при необходимости поправить порты
npm ci                        # или: npm install
npx playwright install chromium

npx playwright test           # весь набор: API + UI
```

Другие варианты:

```bash
npx playwright test --project=api          # только API (быстро, ~3 с)
npx playwright test --project=ui-chromium  # только UI
npx playwright test --grep @smoke          # критический путь
npx playwright test --grep @known-defect   # только тесты на известные дефекты
npx playwright test tests/ui/checkout.spec.ts:19   # один тест
npx playwright test --shuffle              # случайный порядок (проверка независимости)

npx playwright show-report reports/html    # открыть HTML-отчёт
npx tsc --noEmit                           # проверка типов
```

Требование «каждый тест запускается отдельно, в любом порядке и параллельно»
проверено: набор проходит при `--workers=1`, при полностью параллельном запуске и
в случайном порядке (`--shuffle`).

### Как устроен набор

```
tests/
├── api/
│   ├── checkout-order.spec.ts   # критический путь через API: заказ, суммы, позиции
│   ├── cart.spec.ts             # корзина: количество, слияние, Thor Hammer, границы
│   ├── catalog.spec.ts          # поиск, фильтр по цене, сортировка, 404
│   ├── access.spec.ts           # доступ к чужим заказам, авторизация, валидация
│   └── known-defects.spec.ts    # BUG-01…BUG-04, помечены test.fail()
└── ui/
    ├── checkout.spec.ts         # сквозной заказ через мастер, пересчёт итога
    ├── catalog.spec.ts          # поиск и сортировка в интерфейсе
    └── known-defects.spec.ts    # BUG-05, помечен test.fail()
src/
├── api/shop-api.ts              # типизированный клиент Toolshop API
├── data/factories.ts            # генерация пользователей, адрес из postcode-lookup
└── fixtures/                    # фикстуры (api, authed, product), хелперы UI, матчеры
```

Селекторы - только `data-test`-атрибуты приложения (286 штук в разметке), без
привязки к CSS-классам и структуре DOM.

Про количество: в ТЗ ориентир «5-10 содержательных автотестов», здесь их 24.
Это не попытка взять объёмом - в наборе 8 сценариев (критический путь через API
и через UI, корзина, каталог, доступ, валидация), а остальные тесты - регрессии
на конкретные дефекты и граничные значения. Ориентир в ТЗ задан как «порядок
величины, а не норма», и ценность здесь в том, что каждый тест проверяет
результат операции, а не наличие кнопки.

## 5. Тестовые данные

- **Свой покупатель на каждый тест**, регистрация через API с уникальным e-mail.
  Демо-аккаунты не используются: после `MAX_LOGIN_ATTEMPTS = 3` неудачных входов
  аккаунт блокируется, и общий пользователь превращает один негативный тест в
  каскад падений.
- **База между тестами не сбрасывается.** Тесты не делят состояние: у каждого своя
  корзина и свой заказ.
- **`globalSetup` с `migrate:fresh --seed` не используется.** Сброс на старте
  скрывал бы загрязнение данных между тестами и добавлял 30+ секунд к каждому
  прогону. Вместо этого набор устойчив к остаткам предыдущих запусков: товар
  подбирается по факту наличия (`GET /products/{id}` - `in_stock`).
- **Адрес заказа строится из `GET /postcode-lookup`**, а не выдумывается: API
  валидирует соответствие города/региона стране, и придуманный адрес даёт 422.
- Остаток товара уменьшается каждым заказом, поэтому **перед прогоном желателен
  `migrate:fresh --seed` + `cache:clear`**. Тесты подбирают товар в наличии, но
  после десятка прогонов популярные дешёвые позиции могут закончиться.

Пароли и адреса - только для локального инстанса. `.env` не коммитится, в
репозитории лежит `.env.example`.

## 6. Ожидаемые падения

Пять тестов помечены `test.fail()` и **должны падать** - каждый воспроизводит
подтверждённый дефект. В отчёте они отображаются как «expected failure»:

| Тест | Дефект | Фактическое поведение |
|---|---|---|
| `tests/api/known-defects.spec.ts` › BUG-01 a product with zero stock cannot be ordered | BUG-01 | товар с остатком 0 добавляется (200) и заказывается (201) |
| `tests/api/known-defects.spec.ts` › BUG-02 cart quantity is limited by available stock | BUG-02 | 26 шт. при остатке 25 принимаются, остаток уходит в минус |
| `tests/api/known-defects.spec.ts` › BUG-03 an empty cart cannot be turned into an order | BUG-03 | пустая корзина - заказ на 0.00 (201) |
| `tests/api/known-defects.spec.ts` › BUG-04 another customer's cart cannot be consumed | BUG-04 | чужой `cart_id` - заказ создаётся (201) |
| `tests/ui/known-defects.spec.ts` › BUG-05 one click on "Confirm" places the order | BUG-05 | заказ создаётся только вторым нажатием Confirm |

Ожидаемый результат финального прогона: **24 теста, 19 passed, 5 expected failures,
0 unexpected failures**. Любое другое число падений - регрессия.

Как читать отчёт и trace - в [`reports/README.md`](reports/README.md).

Если дефект исправят, соответствующий тест начнёт **падать с сообщением
«expected to fail but passed»** - это сигнал снять `test.fail()`.

Тест на BUG-05 использует двухшаговое подтверждение как обход, поэтому сквозной
сценарий заказа в UI остаётся зелёным и продолжает охранять остальную часть мастера.

## 10. Ограничения этого репозитория

- Прогон выполнен только в Chromium. Проектов Firefox и WebKit в конфигурации
  нет: в `playwright.config.ts` заведены только `api` и `ui-chromium`.
- Гостевое оформление заказа и способы оплаты bank-transfer / credit-card
  автотестами не покрыты (TC-27, TC-28 в [TEST_CASES.md](TEST_CASES.md)).
- Тесты не проверяют админку, аренду, контактную форму, 2FA и PDF-инвойсы - вне
  области проверки.
- `reports/` соответствует финальному коммиту; после любого изменения кода тестов
  отчёт нужно перегенерировать (`npx playwright test`).
