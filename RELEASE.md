# RELEASE - решение о готовности

**Версия:** `SPRINT=sprint5`, тег `2.5`, commit `9e7736c3841ec2bbb9a6822c9e6602353b7b9a65`.
**Проверенная область:** каталог - корзина - оформление заказа (+ вход/регистрация в объёме, нужном для этих сценариев).
**Дата решения:** 2026-11-03.

---

## Решение

### ❌ Выпускать проверенную часть в текущем виде нельзя.

Два дефекта блокируют релиз, ещё три должны быть исправлены до выпуска. Критический
путь «найти товар - положить в корзину - оформить заказ» **технически проходит**
(и через API, и через UI), но:

1. **BUG-02 (Critical)** - заказ принимается в количестве больше остатка, остаток
   уходит в минус. Это порча данных, а не только UX: цена ошибки растёт с каждым
   заказом.
2. **BUG-05 (High)** - в UI заказ не создаётся с первого нажатия «Confirm», при
   этом интерфейс показывает «Payment was successful». Пользователь получает
   ложное подтверждение и уходит.

BUG-01 (продажа отсутствующего товара), BUG-03 (заказы на 0.00) и BUG-04 (заказ из
чужой корзины) - High, должны уйти в тот же релиз, но сами по себе релиз не
останавливают: у них есть либо обход, либо ограниченное влияние.

## Обоснование

### Что проверено

| Область | Результат |
|---|---|
| Каталог: поиск, фильтр по цене, сортировка, карточка | Работает, инварианты соблюдаются (TC-03…TC-06, TC-18, TC-19) |
| Корзина: добавить, изменить количество, удалить, слить позиции | Работает, суммы пересчитываются (TC-07, TC-08, TC-16) |
| Бизнес-правило «один Thor Hammer» | Работает, отклоняется 400 с понятным текстом (TC-09) |
| Валидация количества (0 и отрицательное) | Работает, 422 (TC-10) |
| Оформление заказа через API | Работает: заказ создаётся, сумма и позиции сохраняются верно (TC-01, TC-02) |
| Оформление заказа через UI | Работает **со второго нажатия** Confirm (TC-15) |
| Валидация адреса и способа оплаты | Работает: 422 на чужие сочетания страны/города/индекса (TC-13) |
| Изоляция заказов между покупателями | Работает: чужой заказ - 404 (TC-11) |
| Обязательность аутентификации при оформлении | Работает: 401 (TC-12) |

Итог прогона: **24 автотеста, 19 проходят, 5 падают ожидаемо** - по одному на
каждый подтверждённый дефект. См. `reports/html/index.html`.

### Что блокирует релиз

| Дефект | Почему блокирует | Что нужно |
|---|---|---|
| BUG-02 | Порча данных: отрицательный остаток, продажа сверх склада | Проверка остатка при добавлении в корзину **и** при создании заказа; ответ 409 с доступным количеством |
| BUG-05 | Критический путь в UI не завершается; ложный сигнал успеха | Идемпотентная проверка оплаты: `finishFunction` должен получать результат текущей проверки, а не состояние предыдущего вызова |
| BUG-01 | Продажа товара со нулевым остатком | Отклонять добавление при `stock = 0` (4xx), не полагаться на блокировку кнопки в UI |
| BUG-03 | Мусорные заказы на 0.00 | Запрет оформления пустой корзины в сервисе |
| BUG-04 | Отсутствует контроль доступа к корзине | Привязка корзины к покупателю либо подписанный `cart_id` + описание модели угроз |

### Что не проверено (и насколько это рискованно)

| Не проверено | Риск |
|---|---|
| Гостевое оформление заказа (TC-27) | **Высокий**: отдельная ветка checkout, ошибки в ней не видны |
| Валидация bank-transfer и credit-card (TC-28) | **Высокий**: правила валидации заметные, ошибка = отказ оплаты |
| Скидки (eco, additional discount) (TC-29) | **Средний**: влияют на итог заказа, то есть на деньги |
| Блокировка аккаунта после неудачных входов (TC-30) | **Средний**: влияет на поддержку и на воспроизводимость тестов |
| Кросс-браузерность (Firefox, WebKit) | **Средний**: проекты не заведены, прогон не выполнялся |
| Гонка при остатке 1 | **Низкий/средний**: требует нагрузочного сценария |
| Отмена заказа и возврат остатка | **Не оценивал**: вне области |
| Админка, аренда, контактная форма, 2FA, PDF-инвойсы | **Не оценивал**: вне области по заданию |

Проверенная часть покрывает основной путь покупки, но **не покрывает** две ветки
оформления (гость, другие способы оплаты) и скидки. Это значит, что даже после
исправления блокеров нельзя утверждать, что checkout готов целиком - только что
основной путь стабилен.

## Следующие шаги (в порядке приоритета)

1. **Исправить BUG-02 и BUG-05** - без этого релиз невозможен. После исправления
   снять `test.fail()` в `tests/api/known-defects.spec.ts` и
   `tests/ui/known-defects.spec.ts`: тесты начнут падать с «expected to fail but
   passed», это и будет сигналом, что фикс работает.
2. **Исправить BUG-01, BUG-03, BUG-04** - все три локализуются в одном месте:
   валидация корзины и владельца в `InvoiceService`/`CartService`.
3. **Показать ошибку оформления пользователю** (наблюдение 3 в `BUGS.md`):
   сейчас `createInvoice` глотает ошибку, и любой 422 выглядит как «ничего не
   произошло». Это делает BUG-05 ещё опаснее.
4. **Дописать контрактные тесты на гостя и два способа оплаты** (TC-27, TC-28) -
   две не покрытые ветки того же критического пути.
5. **Починить процедуру сброса данных** (BUG-06): добавить `cache:clear` в
   документированную команду или в `migrate:fresh`-обёртку.
6. **Встроить прогон в CI**: поднять compose на закреплённом теге, дождаться
   `/status`, выполнить `cache:clear`, затем `npx playwright test`; публиковать
   `reports/html` как артефакт сборки. Локально этот шаг не проверялся.
7. **Завести и прогнать Firefox/WebKit**: добавить проекты в
   `playwright.config.ts` и выполнить `npx playwright test --project=firefox`.
8. **Добавить контрактную проверку остатка на уровне БД** (только для админа):
   сейчас нет способа увидеть остаток через API, а он нужен и тестам, и поддержке.

## Условия для повторного решения

Релиз можно считать готовым, когда одновременно:

- [ ] BUG-02 и BUG-05 исправлены, соответствующие тесты зелёные без `test.fail()`;
- [ ] BUG-01, BUG-03, BUG-04 исправлены или явно приняты продуктом с описанием риска;
- [ ] TC-27 и TC-28 покрыты автотестами;
- [ ] полный прогон зелёный, отчёт приложен к финальному коммиту.

## Оговорка про объём

Проверена только заявленная область. Админка, аренда, контактная форма, 2FA и
PDF-инвойсы не проверялись - по ним **нет оснований** ни для запрета, ни для
разрешения релиза. Если релиз включает эти части, решение выше к ним неприменимо.
